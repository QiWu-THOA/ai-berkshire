# pi-toolkit

AI Berkshire 在 [pi](https://github.com/earendil-works/pi) 下的成本审计与研究子代理工具集。

Claude Code 用户不需要这个目录——你们的对应能力是 `/cost`、`/compact` 和 Task 子代理。
本目录是 **pi 专属**，由 `install.sh` 安装到 `~/.pi/agent/`。

```bash
./install.sh            # 安装
./install.sh --check    # 只检查，不写文件
```

---

## 为什么要这些东西

本机真实账本（19 个会话、1563 次调用的实测值，不是估算）：

| 成本项 | 占比 | 说明 |
|---|---:|---|
| 未命中输入 | 39.7% | 每次新增的工具结果 / 用户输入，按全价计费 |
| **缓存读（Σ上下文）** | 29.4% | 重复发送的上下文前缀 |
| 输出 + 推理 | 30.9% | 单价最贵；推理占输出的 40.8% |

**关键等式：`Σ上下文 = 调用次数 × 每次上下文`。**

最贵的单个会话：654 次调用、**平均每次带 88.8k 上下文、峰值 283k**，一个会话占全部花费的 51.8%。

而缓存命中率已经 89%、单价已经是最便宜的 flash 档——**这两项都没有压缩空间了**。剩下的杠杆只有两个乘数：调用多少次、每次带多少上下文。


## 命令

| 命令 | 作用 |
|---|---|
| `/cost` | 当前会话账本：成本构成、Σ上下文、命中率、推理占比、按模型拆分、自动诊断 |
| `/cost all` | 全部会话汇总 + 最贵会话排行 |
| `/cost clear` | 清掉面板 |
| `/guard` | 查看触发点：`max(min(窗口×比例, 上限), 下限)` |
| `/guard 0.6` | 调比例 |
| `/guard compact` | 立即手动压缩 |
| `/guard off` / `on` | 开关自动压缩（状态行保留） |

命令行参数：`--guard-ratio <0.05-0.95>`、`--guard-max <token>`、`--guard-off`。

诊断日志写在 `~/.pi/agent/guard.log`（只在关键决策点写，量很小）。

| **自动压缩真的成功** | ❌ **未验证** | 所有测试都在 `-p` 非交互模式下跑，`compact()` 是 fire-and-forget，进程退出会把它杀掉（`This operation was aborted`）。**需要在真实交互式会话里确认** |

| 子代理隔离上下文 | ✅ **已验证** | 端到端派发 `web-scout` 成功；固定开销 ≈ 4.2k 输入 token |

### 自动压缩的 30 秒自测（需要你来做）

我的测试环境无法模拟交互式 TUI，所以这一步只能你来：

1. 正常开一个 pi 会话，干点会让上下文涨过 60k 的活（或直接 `/guard 0.2` 把阈值压到 26k，更快）
2. 观察 footer 状态行：`ctx` 变黄 → 变红
3. 一轮结束后看 `~/.pi/agent/guard.log`：
   - 出现 `FIRE tokens=...` → 触发逻辑正常
   - 接着出现 `DONE before=...` → **压缩成功，自动化可用**
   - 出现 `ERROR ... aborted` → 自动化在交互模式下也不可用，**请用 `/guard compact` 手动压**，并靠「按阶段开新会话」的纪律兜底

**无论哪种结果都不影响已经生效的部分**：`/cost` 的可见性、`/guard compact` 手动压缩、子代理隔离上下文、AGENTS.md 里的会话分段纪律。

## 已知约束（都是实测撞出来的，不是推测）

### 1. pi 认为 deepseek-v4-flash 的窗口是 1,000,000

不是 131k。后果：**内置自动压缩阈值 = 窗口 − reserveTokens ≈ 984k，实际永远不会触发**。

这正是「平均上下文 88.8k、峰值 283k」的根因——不是没人管，是阈值本身形同虚设。

所以本工具不用「窗口比例」单独做判据，而是 `min(窗口 × 比例, 绝对上限 60000)`：窗口只用来给小窗口模型做安全下限。

### 2. 不能靠 `compaction.reserveTokens` 解决问题

它是**绝对值**，同时身兼两职：

- 触发阈值 = `contextWindow − reserveTokens`
- 摘要输出上限 = `min(0.8 × reserveTokens, model.maxTokens)`

本机模型窗口混杂（1M / 131k / 32k），**没有任何一个 reserveTokens 能同时适配**：

| reserveTokens | 1M 窗口 | 131k 窗口 | 32k 本地模型 |
|---|---|---|---|
| 16384（默认） | 984k 才压，等于不压 | 115k 才压，太晚 | 16k 触发 ✅ |
| 940000 | 60k 触发 ✅ | **阈值变负 → 每轮都压** | **阈值变负 → 每轮都压** |
| 71072 | 929k，等于不压 | 60k 触发 ✅ | **阈值变负 → 每轮都压** |

结论：这个设置项在本机不可用，只能靠扩展做按模型正确的判断。

### 3. `ctx.compact()` 在事件处理器里不可用

两个坑，都实测踩过：

- **在 `turn_end`（agent 还在跑）里调** → 摘要调用被当前 run 的中断信号杀掉，`Turn prefix summarization failed: This operation was aborted`，**并且把整个 run 一并中断**
- **在 `agent_settled`（run 已停）里调** → 仍然是 `aborted`
- **在命令处理器 `/guard compact` 里调** → 仍然是 `aborted`

后两个大概率是 `-p` 非交互模式下进程退出所致（`compact()` 不等待完成），但我**无法在无 TTY 环境里排除**，故标为未验证。详见上面「自动压缩的 30 秒自测」。

### 4. 压缩有一个硬下限

pi 压缩时要向前找切点，保留 `keepRecentTokens`（默认 20000）。**上下文不到这个量就根本不存在合法切点**，调用会报 `Nothing to compact (session too small)` 并中断当前 run。

所以触发点取 `max(计算值, 16000)` — 低于这个数一律不尝试。

### 5. 回调里的 ctx 会失效

`onComplete` / `onError` 是异步触发，此时捕获的 `ctx` 已失效，访问 `ctx.ui` 会抛
`This extension ctx is stale after session replacement or reload`，**并直接崩掉进程**。

**规矩：这两个回调里只许碰本地状态和日志文件，绝不碰 `ctx`。**

### 6. subagent 扩展是第三方代码，不 vendored

`extensions/subagent/` 来自 pi 官方示例（35KB），由 `install.sh` 从 pi 包目录**复制**（不是软链——软链会在 pi 升级后静默断掉）。因此：

- 不要在仓库里编辑它，改官方上游
- pi 升级后重跑 `./install.sh`

跑一份同类任务，用 `/cost` 对比这两个数（绝对值比总价更重要）：

| 指标 | 优化前（实测基线） | 目标 |
|---|---:|---:|

| 缓存命中率 | 89.1% | 保持 > 90%（**这项已到底，别折腾**） |

## 纪律（比工具更重要）

工具只能告警，钱是用法决定的。四条硬规则，已写入 `~/.pi/agent/AGENTS.md`：

1. **长任务按阶段开新会话**，中间产物落盘，下一阶段只读需要的那一段
2. 上下文超 60k 就 `/compact`（内置自动压缩要等 ~984k，等于没有）
3. 需要读长文档 / 做检索时**派子代理**，别把原始噪音留在主会话
4. 机械步骤（抓数、筛选、格式化）走免费池或 flash；只有最终判断与成文用高价档

**子代理是这套里最大的杠杆**：串行侦察实测跑到 141 次调用、平均 87.6k 上下文；同样工作拆成 4 个并行子代理，主会话可全程保持 20k 以内——因为两个乘数同时变小。
